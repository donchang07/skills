# dns-to-prd — DN솔루션즈용 PRD 작성기

이 스킬은 to-prd의 절차·검사 스크립트·출력 구조를 그대로 쓰고, DN솔루션즈 사업에 필요한 규칙을 덧붙인다. 새로 만드는 것은 세 가지다.

1. **DN 도메인 팩**: 역할, 통화·언어·거점 기본값, 용어, 기밀 등급, 합성 데이터 원칙
2. **계산 모델 계약(CM-\*)**: 예측·시뮬레이션·최적화가 맞았는지 bkit이 판정할 수 있게 하는 계약
3. **DN 점검 기준**: 게이트 검토에 더하는 DN 전용 결함 기준

품질 기준은 하나다.

> 이 PRD만 받은 bkit이 DN솔루션즈의 어떤 역할을 위해 어떤 화면을 만들고, 화면 안의 예측·시뮬레이션·최적화가 어떤 데이터로 어떻게 계산되며 어느 수준이면 합격인지, 어떤 값을 사람이 확정하는지, 어떤 데이터가 합성이고 실데이터로 바꾸려면 무엇이 필요한지 알 수 있다.

## 사용 범위

| 사용한다 | 사용하지 않는다 |
|---|---|
| DN솔루션즈 임직원 업무 앱(영업·딜러 견적, 기술영업, 생산계획, 구매, 서비스·디엔서비스, 재무, HELLER 협업, 경영 현황판) | 장비 소프트웨어 자체의 기능 변경(CUFOS, iDOO RMS+ 내부 기능, DNVS, CNC 제어). to-prd-equip은 반도체 장비 표준(SECS/GEM 등) 기준이라 공작기계에 그대로 맞지 않는다. 이 경우 작업을 멈추고 "공작기계 장비 소프트웨어용 PRD 스킬이 아직 없다"고 보고한다 |
| 임원 바이브코딩 실습 PRD(합성 데이터, 정적 화면) | 일반 이해관계자용 기획서, 회사 단위 교육 자료 한 벌 |

DN솔루션즈와 무관한 PRD 요청이면 to-prd를 쓰라고 안내한다.

## Step 0 — to-prd 찾기와 읽기

1. 설치된 to-prd를 찾는다. 다음 순서로 `to-prd/SKILL.md`를 검색한다: `~/.claude/plugins/` 아래, `~/.claude/skills/to-prd/`, 프로젝트 `.claude/skills/to-prd/`. 찾은 폴더를 `TOPRD`라 부른다.
2. 없으면 멈추고 설치 명령 두 줄을 안내한다: `/plugin marketplace add donchang07/skills`, `/plugin install to-prd@donchang-skills`.
   - 찾은 폴더에 `scripts/`(validate_prd.mjs·render_prd_html.mjs·check_output.mjs)가 없으면(동기화된 스킬 사본은 스크립트가 빠져 있을 수 있다) `git clone --depth 1 https://github.com/donchang07/skills /tmp/donchang-skills`로 받아 `TOPRD=/tmp/donchang-skills/skills/to-prd`로 바꾼다. 받을 수 없으면 검사 없이 진행하지 말고 보고에 "검사 스크립트 없음"을 쓴다.
3. `TOPRD/SKILL.md` 전체를 읽고 그 Step 0~9를 그대로 따른다. 참고 파일·스크립트 경로는 `TOPRD` 기준이다(예: `node TOPRD/scripts/validate_prd.mjs`).
4. 아래 DN 규칙은 to-prd의 해당 Step에 **추가로** 적용한다. to-prd 규칙과 부딪히면 to-prd의 검사 스크립트가 통과하는 쪽을 택하고, DN 내용은 사라지지 않게 다른 위치(11.3 제품 가정 또는 12·13장)로 옮긴다.
5. PRD 메타에 `DN 오버레이: dns-to-prd v1.2`를 한 줄 더한다.

## Step 1 보강 — DN 도메인 팩 설치

`docs/00-pm/_conventions.md`를 확인한다. to-prd는 이 파일을 다른 입력보다 먼저 읽는다.

- 없으면 아래 「DN 도메인 팩」 전체로 만든다.
- 있으면 `## DN 도메인 팩` 절이 있는지 본다. 없을 때만 끝에 추가한다. 기존 규칙은 지우거나 고치지 않는다. 기존 규칙과 반대되는 DN 규칙이 있으면 사용자에게 어느 쪽을 따를지 묻는다.
- 팩의 사실(거점·인수·법인)은 공개 보도 기준이며 기준일을 함께 적는다. 사용자가 사내 공식 정보로 정정하면 그 값을 따르고 `[확정·출처: 사용자 YYYY-MM-DD]`로 바꾼다.

| 승인 임원 | 관리자 | 가격·할인·납기 최종 확정 |
| 생산계획 담당 | 일반 | 거점별 생산 배분 |

| 서비스 엔지니어(디엔서비스) | 일반 | 현장 모바일 사용 가능성 |

**거점과 단위.** 거점 코드: `CW`(창원), `BS`(부산), `IN`(인도), `DE`(독일·HELLER). 길이는 mm, 수량은 대, 리드타임·납기는 주 단위를 기본으로 하고 화면에 단위를 함께 표시한다.

**용어.** 화면·버튼·필드 라벨은 현장 용어를 쓴다.

| 용어 | 뜻 |
|---|---|
| 기종 | 공작기계 모델. 공개 제품명을 쓸 수 있다 |
| 옵션·사양 | 기종에 더하는 구성(자동화 장치 포함) |
| 견적·수주 | 딜러·고객에게 낸 가격 제안과 확정 주문 |
| 리드타임·납기 | 주문부터 출하까지 걸리는 기간과 약속한 출하일 |
| 장비 시리얼 | 출하 장비 개별 번호 |
| 알람 | 장비가 보내는 이상 신호 |
| 가동률·사이클타임 | 장비가 일한 비율, 부품 하나를 가공하는 데 걸리는 시간 |
| 자동화 셀 | 팔렛 풀, 바 피더, 갠트리 로더, 자동 공작물 교환장치 등과 장비의 묶음 |

**기밀 등급.** 부록 A의 모든 필드에 등급을 붙인다.

| 등급 | 예 | 규칙 |
|---|---|---|
| 공개 | 공개 제품명, 공개 보도 사실 | 제한 없음 |
| 사내 | 거점별 생산 계획, 조직 | 로그인 필수 |
| 기밀 | 가격, 원가, 할인율, 마진, 고객·딜러 연락처 | 역할별 열람 제한, 화면 출력·내보내기 기록 |
| 제한 | 방산·수출 통제 관련 고객, 도면, 고객 가공 데이터 | 첫 버전에서 다루지 않는다. 비목표(NG)로 고정 |

**합성 데이터 원칙.**

- 실데이터 없이 만드는 첫 버전은 합성 데이터만 쓴다. 이 스킬의 모든 문서는 "가짜 데이터"가 아니라 "합성 데이터"라고 쓴다.
- 합성 데이터의 칸 이름·타입·코드는 실제 원천 시스템과 같은 모양으로 만든다. 원천을 모르면 `[추정]`으로 두고 13장에 확인 요청을 둔다.
- 위치는 `data/*.csv`, 서버 없는 화면용으로 같은 내용의 `data/data.js`를 함께 만든다. `data/README.md`에 "모든 값은 실습용 합성 데이터입니다"를 적는다.
- 예측을 쓰는 앱은 날짜가 있는 기록을 24개월 이상 만든다. 결측·이상치·경계값(0, 최대치, 통화 혼합)을 일부러 넣는다. 생성 규칙과 난수 시드를 README에 적어 다시 만들 수 있게 한다.
- 생성 규칙은 PRD 부록 A 「합성 데이터 생성 규칙」에 숫자로 쓴다: 난수 시드, 기간, 월 건수, 분포, 확률식, 가격·원가·환율 값, 특수 시드(사례 부족·해 없음·오래된 기준일 등). 결측을 넣는 칸은 원래 값으로 결과를 먼저 뽑은 뒤 칸만 비운다고 쓴다.
- **성립 조건**: 생성 규칙 아래에 "정상 시드의 대표 요청은 계산 완료, 특수 시드는 의도한 계산 불가가 된다"를 쓰고, Step 3의 데이터 양 확인으로 증명한다.
- **재현 규칙**: 같은 시드면 누가 구현해도 같은 파일이 나오도록 다음을 숫자로 쓴다. 난수 생성기 알고리즘(예: mulberry32, 외부 패키지 없이 생성 스크립트 안에 구현), 행마다 뽑는 순서, 균등 난수 u를 범주·정수로 바꾸는 식(n개 중 floor(u × n)번째), 확률 판정식(u < p), 결측·경계값을 난수 몇 개로 정하는지와 그때 결과값을 바꾸기 전 값으로 뽑는지. 이것이 없으면 데이터 양 확인이 실제 생성 결과를 보장하지 못한다.
- **검사 실패 시**: 생성 스크립트의 성립 조건·백테스트 검사가 실패하면 다시 뽑지 않고 결과를 출력한 채 실패로 끝내고 13장 결정 요청으로 넘긴다. 통과할 때까지 다시 뽑으면 합격 기준이 의미를 잃는다.
- 합성 데이터 결과는 업무 성과가 아니라 가설이다. 성공 지표(G-\*)의 목표값은 `[가설]`로 둔다.

**성공 지표 후보.** 브리프가 비었을 때 3장 G-\* 후보로 제시한다: 견적 회신 속도, 수주율, 건당 이익, 납기 준수율, 장비 가동률, 고객 대기 일수, 재고 회전, 예측과 실적의 차이. 값은 모두 `[가설]`이다.

## Step 1.5 보강 — 작성 모드 판정

to-prd의 Lean·Full 조건을 DN 업무에 이렇게 적용한다.

- 외부 AI를 부르지 않는 화면 안의 계산(CM-\*)만 있으면 AI 기능으로 보지 않는다. 이 경우 11.4~11.6은 `[해당 없음] — 외부 AI 없음, 계산은 11.7 계산 모델 계약`으로 쓰고 Lean 판정을 막지 않는다.
- 딜러(외부) 역할이 있거나, ERP·CRM·딜러 포털·iDOO RMS+ 등 실제 시스템과 연결하면 외부 연동이므로 Full이다.
- 실습(임원 과정 등)이고 사용자가 "정적 화면, 합성 데이터, 화면 세 개 이하"를 지정했으면 Lean으로 둔다.

## Step 2 보강 — 입력 매핑

to-prd 작업 메모(`_workspace/01_mapping.md`)에 세 표를 더한다.

13. 업무 단계 → 유형(자동화·예측·시뮬레이션·최적화) → CM-\* → 사람이 결정할 것
14. 데이터 엔티티 → 원천 시스템(모르면 `[추정]`) → 합성 여부 → 실데이터 전환 조건
15. 데이터 필드 → 기밀 등급 → 열람 역할

입력에 `docs/01-my-work.md`, `docs/02-ideas.md`, `docs/04-decision.md`(임원 실습 산출물)가 있으면 업무 브리프로 읽는다. `02-ideas.md`의 유형 표가 CM-\*의 출발점이다.

## Step 3 보강 — 11.7 계산 모델 계약

업무에 예측·시뮬레이션·최적화가 하나라도 있으면 11.6 다음에 `### 11.7 계산 모델 계약`을 쓴다. 없으면 `해당 없음 — 자동화만 있음`과 그 이유를 쓴다. 자동화만 있는 PRD는 13장에 "다음 단계에서 붙일 예측·시뮬레이션·최적화 후보"를 하나 이상 남긴다.

|---|---|---|---|---|---|---|---|---|---|---|

공통 규칙:

- 계산 결과 필드와 사람 확정 필드는 부록 A에서 다른 필드다. 확정자·확정 시각·계산과 다를 때 사유 필드를 둔다.
- 결과를 보여 주는 화면마다 계산 방법 한 줄과 데이터 기준일을 표시하는 UI 요소를 둔다.
- 결과를 보여 주는 화면의 상태에 `계산 불가`를 더한다(데이터 부족, 조건을 만족하는 안 없음). 오류가 아니라 정상 동작이며, 사람에게 넘기는 행동을 쓴다.
- 합격 기준 숫자는 근거가 없으면 `[기본값]`이고 13장에 확인 요청을 둔다.

### 유형별 필수 내용

**예측**

- 출력은 숫자 하나가 아니라 범위(하한·중앙·상한)다.
- 계산 방법은 쉬운 말과 방식을 함께 쓴다(예: "같은 산업 고객의 지난 기록으로 추세를 계산 — 이동평균").
- 합격 기준: 백테스트. 합성 데이터의 최근 6개월을 숨기고 예측해 실제 값이 범위 안에 든 비율 `[기본값] 70% 이상`. 백테스트 절차(숨길 시점, 학습 창, 평가 묶음, 묶음 최소 건수, 유효 묶음 최소 수)를 번호로 쓴다.
- **범위 폭과 합격선을 같은 값으로 두지 않는다.** 80% 예측 범위에 적중률 80%를 요구하면 통과가 운에 달린다. 합격선은 명목 포함률보다 10%p 이상 낮게 두거나, 범위를 더 넓힌다(예: 80% 범위 → 합격선 70%).
- 데이터가 기준 기간(`[기본값]` 24개월)보다 짧으면 `계산 불가` 상태.

**시뮬레이션**

- 바꿀 수 있는 조건 목록(이름·단위·최소·최대·기본값)과 고정 가정을 쓴다.
- 출력은 기준안 대비 차이를 함께 보여 주는 비교표다.
- 합격 기준: 같은 입력이면 같은 결과(재현 100%), 조건 최소·최대 경계값에서 오류 0건, 손으로 계산한 표본 3건과 일치.

**최적화**

- 목표 하나(이익 최대, 비용 최소 등)와 우선순위를 쓴다. 목표가 둘이면 가중치 또는 우선순위를 13장 결정으로 둔다.
- 제약을 반드시 지킬 것(하드)과 되도록 지킬 것(소프트)으로 나눈다. 예: 이익 하한, 납기 약속, 거점별 생산 여력.
- 탐색 방법을 쓴다: 전수 탐색, 규칙, 최적화 라이브러리 중 하나. 첫 버전은 후보 수가 작으면 전수 탐색을 기본으로 한다.
- 출력은 추천안 하나, 차선안 둘, 제약 충족표다.
- 해가 없으면 `계산 불가` 상태로 "조건을 만족하는 안 없음"과 가장 덜 어긴 안을 보여 주고, 어느 제약을 풀어야 하는지 표시한다.
- 합격 기준: 작은 사례에서 전수 탐색 정답과 100% 일치, 하드 제약 위반 0건. 작은 사례의 탐색 공간(조건 값 목록과 후보 수)을 숫자로 쓴다.

### 공통 정의

11.7 표 앞에 세 모델이 같이 쓰는 정의를 먼저 쓴다: 기준일(실행 날짜가 아니라 데이터의 마지막 날짜), 계산 창, "비슷한 사례"의 조건(허용 오차, 양 끝 포함 여부, 결측 행 처리), 범위 공식, 원가·이익·기대값 공식과 반올림, 동점 처리 순서. 공식이 없으면 bkit이 구현마다 다른 값을 낸다.

### 데이터 양 확인 (필수)

사례 수 기준(예: 비슷한 사례 10건 미만이면 계산 불가)을 둔 모델은 PRD를 확정하기 전에 생성 규칙이 그 기준을 채우는지 계산으로 확인한다.

1. 생성 규칙을 그대로 구현한 짧은 스크립트를 `docs/00-pm/_workspace/06_seed_check.py`에 쓰고 실행한다(외부 패키지 없이).
2. 출력: 대표 요청의 칸·후보별 최소 사례 수, 계산 불가 칸 수, 최적화의 남은 후보 수와 하드 제약 충족 후보 수, 특수 시드별 결과.
3. 기준 미달이면 월 건수를 늘리거나 사례 기준을 낮추고, 바꾼 값과 이유를 생성 규칙에 쓴다. 결과는 `06_seed_check.txt`에 저장하고 gate 파일에 한 줄로 요약한다.

어림 계산: 칸당 기대 사례 수 = 묶음당 건수 × (허용 오차 안 값의 수 ÷ 전체 값의 수)를 조건마다 곱한 값. 가장자리 칸은 허용 오차 안 값이 줄어드는 점을 함께 본다.

### 표기 규칙 (검사 스크립트 오인 방지)

- 값 목록을 중괄호로 쓰지 않는다. `{0,3,6}`은 미완성 칸으로 판정된다. `0·3·6`처럼 가운뎃점으로 쓴다.
- 14장 feature 분해표의 FR·SC·DATA는 범위(`FR-001~014`)가 아니라 ID를 쉼표로 모두 나열한다.
- 11.1 테스트 줄에서는 실행 명령(`npm test`, `npx playwright test` 등)만 백틱으로 감싼다. 파일 경로·도구 이름에 백틱을 쓰면 check_output.mjs가 CLAUDE.md 블록에 그 값까지 요구한다.
- 「기준일 − 6개월」처럼 달 단위로 빼는 날짜는 말일에서 구현마다 갈린다(10월 31일의 6개월 전). 계산식 대신 결과 날짜를 직접 쓴다(예: 2026-04-30, 기준일이 속한 달에서 6개월 전 달의 말일).

### 검증 연결

to-prd 검사 스크립트는 `[E2E]·[통합]·[단위]·[평가]·[수동]` 라벨만 받는다. 그래서 다음과 같이 연결한다.

- CM-\*의 합격 기준은 `[단위]` SC로 만든다. 예: `[단위] CM-001 백테스트 — 최근 6개월 범위 적중률 70% 이상`.
- 확정·되돌리기·계산 불가 상태는 `[E2E]` SC로 만든다.
- CM 검증 테스트는 11.1의 단위 테스트 명령에 포함한다. 그러면 to-prd의 두 관문(일치율·테스트 통과)이 CM 합격 기준까지 판정한다.
- 11.7 절을 추가한 뒤 `node TOPRD/scripts/validate_prd.mjs`를 실행한다. 스크립트가 11.7 위치 때문에 오류를 내면 같은 표를 `### 11.3 제품 가정` 아래 `#### 계산 모델 계약` 소제목으로 옮긴다.

## Step 4 보강 — 화면과 데이터

- 금액을 보여 주는 UI 요소에는 통화 코드를 함께 표시한다. 환산 금액에는 환율 기준일을 표시한다.
- 부록 A 데이터 표에 열 세 개를 더한다: `원천 시스템`, `실데이터 전환 조건`, `기밀 등급`. to-prd가 요구하는 기존 열은 그대로 둔다.
- 기밀 등급 `기밀` 필드는 역할별 노출 조건을 UI 요소의 `사용자·권한` 열에 쓴다. `제한` 등급 필드가 필요하면 만들지 않고 비목표로 옮긴다.
- 원가·이익률을 숨긴 역할의 화면은 **역산 점검**을 한다. 그 역할에 보이는 숫자(정가·환산 금액·수주 가능성·이익 지수 등)를 함께 놓고 숨긴 값이 식 하나로 풀리는지 본다. 풀리면 그 칸을 순위·단계(높음·보통·낮음)로 바꾸거나, 실습판에서만 위험을 받아들인다고 13장 결정에 쓰고 실데이터 전환 전 조건으로 둔다.
- 계산이 안 되는 경우에도 업무가 이어지도록 "승인 임원 직접 판단" 같은 사람 판단 경로를 둔다. 이때 확정 입력값은 빈 값으로 시작하고 사유를 필수로 한다.
- 테스트 시각을 고정할 때는 과정일·시연일로 고정하고, 정상 시드가 그날 경고(기준일 경과 등)를 내지 않는지 확인한다. 고정 방법은 하나로 쓴다: Playwright `page.clock.install`로 고정하고, 세션 만료처럼 시간이 지나야 하는 상태는 `page.clock.fastForward`로 만든다. 세션 만료 기준(로그인 시각인지 마지막 행동인지)도 쓴다.
- **시험용 이름 규칙**: UI 요소 ID를 `data-testid`로 쓰면 하위 칸과 상태 문구에도 이름 규칙을 둔다. 예: 표의 칸 `요소ID-d6-w12`, 카드 안의 안 `요소ID-opt1`, 기밀 칸 접미 `-cost-krw`·`-margin-rate`, 화면 상태 문구 `SCR-001-STATE-error`(loading·empty·error·forbidden·calc-blocked). 규칙이 없으면 기밀 비노출, 칸 수, 오류·빈 상태 SC를 E2E로 판정할 수 없다.
- 실습 계정 비밀번호를 환경 변수로 받으면, E2E가 비밀번호를 읽는 곳과 환경 변수가 없을 때 시드 스크립트가 할 일(기존 계정 파일 유지, 파일도 없으면 안내 문구를 출력하고 실패)을 11.1에 쓴다.
- 목록 정렬에는 동점 처리(예: 생성 시각 내림차순, 같으면 번호 내림차순)를 쓴다. 테스트 시각을 고정하면 같은 시각 기록이 생기기 때문이다.
- 화면·버튼 라벨은 용어 표의 말을 쓴다.

## Step 5 보강 — 비목표와 결정 요청

브리프에 없어도 다음 비목표(NG-\*)를 기본으로 넣는다. 사용자가 명시적으로 범위에 넣으면 뺀다.

- 제한 등급 데이터(방산·수출 통제 관련 고객, 도면, 고객 가공 데이터)를 다루는 기능
- 첫 버전에서 실제 사내 시스템에 쓰는 기능(읽기 연동도 13장 결정 전에는 만들지 않음)
- 사람 확정 없이 가격·할인·납기를 확정하는 기능

13장에는 데이터 원천 확인과 실데이터 전환 조건을 `D-*` 하나로 묶어 둔다. 임원 발표의 "실제 데이터로 쓰려면 필요한 것"이 이 항목에서 나온다.

## Step 6 보강 — DN 점검 기준

to-prd 독립 검토자에게 넘기는 기준에 아래를 더한다. 검토자에게는 이 표와 PRD만 준다.

| # | 기준 | 어기면 |
|---|---|---|
| DN-1 | 앞부분 문제가 업무 설명(브리프·`01-my-work.md`)과 같다 | Major |
| DN-2 | 화면·버튼 라벨이 DN 용어다 | Minor |
| DN-3 | 가격·할인·납기 등 책임이 따르는 값에 사람 확정 요소가 있다 | Blocker |
| DN-4 | 예측·시뮬레이션·최적화 기능마다 CM-\*가 있고, 합격 기준이 `[단위]` SC로 연결된다 | Blocker |
| DN-5 | 예측 출력이 범위이고, 최적화에 목표·하드 제약·해 없음 동작이 있다 | Major |
| DN-6 | 금액 필드에 통화 코드, 환산 값에 환율 기준일이 있다 | Major |
| DN-7 | 모든 데이터 필드에 기밀 등급이 있고, 제한 등급 필드가 없다 | 제한 등급 필드가 있으면 Blocker, 등급 누락은 Major |
| DN-8 | 합성 데이터 표시와 실데이터 전환 조건(13장)이 있다 | Major |
| DN-9 | 첫 버전 기능 세 가지 이하, 화면 세 개 이하(실습일 때) | Minor |
| DN-10 | 숨긴 기밀 값(원가·이익률)을 그 역할에 보이는 숫자로 역산할 수 없다. 역산되면 13장에 위험 수용과 전환 조건이 있다 | Major |
| DN-11 | 합성 데이터 생성 규칙이 사례 수 기준을 채운다(06_seed_check 결과). 대표 요청이 계산 완료, 특수 시드가 의도한 계산 불가가 된다 | Blocker |
| DN-12 | 예측 합격선이 범위의 명목 포함률보다 낮다 | Major |
| DN-13 | 하위 칸·상태 문구에 시험용 이름 규칙이 있어 기밀 비노출·상태 SC를 E2E로 판정할 수 있다 | Blocker |
| DN-14 | 합성 데이터 재현 규칙(난수 생성기, 뽑는 순서, 변환식)과 검사 실패 시 동작이 있다 | Major |

결함은 to-prd의 적대적 확인을 거쳐 확인된 것만 반영한다.

## Step 7 보강 — 저장

to-prd 저장 절차를 그대로 따른다. 추가로:

- `docs/00-pm/_conventions.md`에 DN 도메인 팩이 있는지 다시 확인한다.
- CM-\*가 있으면 `CLAUDE.md` to-prd 블록 아래, 마커 밖에 다음 블록을 만들거나 갱신한다. to-prd 마커 안은 건드리지 않는다.

```markdown
<!-- dns-to-prd:begin — docs/PRD.md에서 생성됨 -->
## DN 실행 규칙
- 계산 모델은 PRD 11.7 CM-*의 계산 방법·출력 형식을 따른다. 예측은 범위로, 최적화는 추천안·차선안·제약 충족표로 보여 준다.
- CM-* 합격 기준 테스트는 11.1 단위 테스트 명령에 포함하고 Check 단계에서 실행한다.
- 계산 결과와 사람 확정 값은 다른 필드에 저장한다. 금액에는 통화 코드, 환산 값에는 환율 기준일을 붙인다.
- 데이터는 data/ 의 합성 데이터만 쓴다. 기밀 등급 '제한' 데이터는 만들지 않는다.
<!-- dns-to-prd:end -->
```

## Step 8 보강 — 보고

to-prd 보고 순서 뒤에 세 줄을 더한다. 현업 임원이 읽으므로 쉬운 말로 쓴다.

1. 계산 모델: CM-\*마다 유형, 돕는 결정, 합격 기준 한 줄
2. 실데이터로 쓰려면 필요한 것: 13장의 원천 확인·전환 조건 요약
3. 기밀 판정: 기밀 등급 필드 수와 비목표로 뺀 제한 등급 항목

## 원칙

- to-prd의 절차·검사·정본 규칙을 바꾸지 않는다. DN 규칙은 그 위에 더한다.
- 예측·시뮬레이션·최적화는 합격 기준이 있어야 계약이다. 자동화에서 멈추지 않는다.
- 마지막 결정은 사람이 한다. 계산 값과 확정 값을 섞지 않는다.
- 합성 데이터 결과를 성과라고 쓰지 않는다.
- 회사 사실은 출처와 기준일을 붙이고, 사내 정보로 정정되면 정정값을 따른다.
- 장비 소프트웨어 변경은 이 스킬의 범위가 아니다.
