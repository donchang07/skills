# 작업 규모에 맞춘 협업

전체 개편, 신규 제작, 역할별 병렬 작업, 부분 재실행 때 읽는다. 공통 내용·브랜드·검증 계약은 Codex와 Claude Code에서 같다. Codex에서는 `$chang-ppt`, Claude Code에서는 `/chang-ppt`로 호출한다. 현재 환경에 제공된 역할·위임 도구만 사용하고, 위임 도구가 없으면 순차 실행하되 병렬 실행했다고 보고하지 않는다.

## 모드 선택

| target_mode | 예 | 실행 방식 |
| --- | --- | --- |
| 작은 변경 | 정렬, 서식, 문구 몇 개, 특정 장 좌표 | 팀을 만들지 않는다. 메인이 관련 규칙만 읽고 수정한 뒤 `chang-ppt-qa`만 호출한다. |
| edit_deck (전체 개편) | 기존 강의안 구조·스토리·도식 재설계 | 아래 팀 흐름 전체 |
| new_deck | 새 강의·발표 제작 | 아래 팀 흐름 전체 |
| skill_update | 이 스킬 자체 개선 | 팀을 쓰지 않는다. 지침·참조·도구·트리거와 설치본·저장소 사본의 영향 범위를 대조해 필요한 항목만 고치고 `scripts/check_skill.py`를 실행한다. |

판단이 애매하면 작은 변경으로 시작한다. 변경 범위가 3장 이상의 구조·내용 재설계로 커지면 팀 흐름으로 전환한다.

## Claude Code 팀 구성

**실행 모드:** 서브에이전트 위임 + 생성·검증. 단계마다 결과를 파일로 넘기므로 에이전트끼리 대화할 필요가 없다. 사용자 정의 에이전트는 `~/.claude/agents/`에 있다.

| 에이전트 | 모델 | 맡는 일 | 쓰기 범위 |
| --- | --- | --- | --- |
| `chang-ppt-researcher` | sonnet | 주장별 근거·출처·확인 상태 | `{RUN}/01_*` |
| `chang-ppt-story-designer` | opus | 원본 진단, 덱 논리, 장별 명세, 용어 사전, narrative 계약 | `{RUN}/01_designer_*`, `{RUN}/02_*` |
| `chang-ppt-builder` | opus | 명세대로 PPTX 제작·수정 | 결과 PPTX, `{RUN}/03_*` |
| `chang-ppt-qa` | sonnet | 렌더·정적 검사·명세 대조, 판정만 | `{RUN}/04_*`, `{RUN}/renders_v{N}/` |

플러그인으로 설치한 경우 에이전트 이름은 `chang-ppt:chang-ppt-builder`처럼 플러그인 이름이 앞에 붙는다. 사용 가능한 에이전트 목록에서 실제 이름을 확인해 호출하고, 하나도 없으면 같은 역할 정의를 기본 서브에이전트에 전달해 실행한 사실을 기록한다.

부모(메인)가 공용 계약·통합·최종 판정과 사용자 보고를 소유한다. 같은 PPTX를 두 에이전트가 동시에 쓰지 않는다. QA는 제품을 고치지 않는다.

## 작업 폴더

- `{RUN}` = 대상 프로젝트(현재 작업 디렉터리)의 `_workspace/chang-ppt/{YYYYMMDD}_{덱이름}/`. 이 스킬의 설치 폴더를 작업 폴더로 쓰지 않는다.
- 파일 이름은 `{단계}_{에이전트}_{산출물}` 형식(예: `02_designer_spec.md`). 결과 PPTX는 사용자가 지정한 경로, 없으면 원본 옆에 `{원본이름}_chang_v{N}.pptx`로 둔다.
- `{RUN}/00_packet.md`에 작업 패킷을 먼저 쓴다: target_mode, 청중·목적·시간·슬라이드 수, 원본 경로와 SHA-256, 기준 스킬 경로, 확정된 사용자 결정, 결과 경로, 완료 기준. 모든 에이전트 프롬프트에 이 파일 경로를 넘긴다.

## 흐름

1. **준비 (메인)**: 0단계 확인 후 `00_packet.md` 작성. 청중·목적이 없으면 합리적 가정을 적고 진행한다.
2. **조사·진단 (병렬)**: 한 메시지에서 `chang-ppt-researcher`와 (edit_deck이면) `chang-ppt-story-designer`의 진단을 함께 호출한다. 사용자 자료만으로 충분하고 새 사실 주장이 없으면 researcher를 생략한다.
3. **설계**: `chang-ppt-story-designer`가 `02_designer_spec.md`와 용어 사전 `02_designer_terms.json`을 쓴다. 메인은 장별 한 줄 메시지 목록을 사용자에게 보여 주되, 사용자가 사전 검토를 원했을 때만 기다린다. 그 외에는 기존 승인 범위 안에서 바로 진행한다.
4. **제작**: `chang-ppt-builder`가 결과 PPTX v1을 만든다.
5. **검증**: `chang-ppt-qa`가 렌더·정적 검사·용어 순서 검사(`check_terms.py`)를 거쳐 `04_qa_report_v1.md`를 쓴다.
6. **수정 반복**: `실패` 장이 있으면 수정 대상에 따라 builder(화면 문제) 또는 designer→builder(내용 문제)를 다시 호출하고 QA를 다시 돌린다. 수정·재검증은 최대 2회. 남은 실패는 통과로 바꾸지 않고 보고한다.
7. **완료 (메인)**: 최종 PPTX 저장 → 렌더·QA 보고서 확정 → `{RUN}/05_manifest.json` 작성(원본·결과 SHA-256, 기준 스킬 경로, 렌더러·글꼴, 실제 확인한 슬라이드 ID와 담당, 통과/실패/not_run) → 사용자 보고.

사용자 보고에는 결과 경로, 장별 메시지 요약, `자료 확인 필요` 장, 남은 실패·not_run 범위를 넣는다. 실제 확인하지 않은 렌더링이나 PowerPoint 동작을 통과라고 하지 않는다.

## 부분 재실행

- 0단계: 같은 덱의 `{RUN}`이 있으면 후속 요청으로 본다. "3장만 다시", "이 도식 수정" → 해당 장 ID만 designer(내용) 또는 builder(화면) 재호출 → 변경 장만 QA. 결과는 새 버전 파일로 남기고 이전 결과를 덮어쓰지 않는다.
- 새 원본이나 새 주제가 들어오면 새 `{RUN}`을 만든다.
- 마스터·글꼴·공통 배치를 바꾸면 영향을 받는 전체 장을 다시 QA한다. 변경하지 않은 장의 이전 PNG는 슬라이드·마스터·글꼴·렌더 환경이 같을 때만 재사용한다.

## 오류 처리

- 일시적 도구 오류는 원인을 확인한 뒤 1회 재시도한다. 사용량 한도·권한 거부처럼 다시 해도 같은 실패는 재시도하지 않고 `{RUN}`에 남은 산출물을 확인해 보고한다.
- 에이전트가 멈추면 메인은 직접 확인한 사실만 대신 반영하고, 에이전트의 판단(어떤 장을 왜 삭제했는지 등)을 추측해 채우지 않는다.
- QA가 렌더링하지 못하면 정적 검사 결과만으로 통과 처리하지 않고 `not_run`으로 보고한다.

## Codex 하네스가 있는 프로젝트

프로젝트 루트에 `.agents/skills/harness/SKILL.md`가 있으면 그 runtime-guide.md의 init → ID 등록 → 작업 배정 → 결과 등록 절차를 따르고, 역할 정의는 프로젝트 `.codex/agents/`에서 읽는다. Claude Code에서는 이 절차를 강제하지 않고 위의 Claude Code 팀 구성을 쓴다.

## 테스트 시나리오

1. **신규 제작**: "CEO 대상 생성형 AI 도입 전략 20분 발표 만들어줘" → researcher·designer 순차 → builder v1 → QA → 실패 장만 수정 v2 → manifest와 보고.
2. **전체 개편**: 기존 강의안 경로 + "스토리 다시 짜줘" → researcher ∥ designer 진단 병렬 → 설계 → 제작 → QA.
3. **작은 변경**: "5장 표 가운데로" → 팀 없이 메인 수정 → QA만 호출.
4. **오류 흐름**: QA가 2회 연속 같은 장 넘침 실패 → 3회차 없이 남은 실패와 원인을 보고(분할 제안 포함).
