# 유형 카탈로그

distiller는 유형 선택에, builder는 배치에, 심사자는 구조 적합성 판정에 쓴다. 모든 유형은 [visual-system.md](visual-system.md)의 공통 계약 위에서 그린다.

## 선택 표

| 유형 | 언제 | 쓰지 말 때 |
| --- | --- | --- |
| linear-process | 순서가 핵심인 3~7단계 | 주체가 여럿이고 넘김이 핵심일 때(swimlane) |
| cycle | 끝이 다시 시작으로 이어지거나 단계마다 피드백이 돌아올 때 | 되돌림이 1개뿐이면 linear + 점선 하나 |
| swimlane | 2~6개 주체 사이에서 일을 넘기는 순서와 책임 | 주체가 1개, 또는 단계가 3개 이하 |
| timeline | 날짜·분기·버전 등 시간축이 의미를 가질 때 | 순서만 있고 시점이 없으면 linear-process |
| comparison | 이전/이후, 기존/신규, A안/B안을 항목별로 대비 | 항목이 1개면 두 박스 대비로 충분 |
| architecture | 층·구성요소와 그 사이의 호출·데이터 흐름 | 시간 순서가 핵심이면 process |
| hub-spoke | 한 주체가 여러 대상에 작용(에이전트가 여러 도구를 대신 실행) | 대상 사이의 관계가 중요하면 architecture |
| decision | 조건에 따른 분기와 결과 | 분기 1개면 process에 decision 노드 하나 |

## 유형별 계약

### linear-process (그림 예: 쉐브론 STEP 1~4)
- 필수: 단계 노드 3~7개, `reading_path`가 노드 순서와 같다.
- 배치: 한 줄 가로 등간격. 단계 번호 또는 쉐브론 모양으로 순서를 보이고, 화살표와 번호를 중복으로 쓰지 않아도 된다. 각 단계 아래 설명은 2~4줄 이내 불릿.
- 강조: focal 단계만 강조색, 나머지는 같은 색 계열.

### cycle (그림 예: PLAN→DESIGN→DEVELOP→TEST→DEPLOY + Continuous Improvement)
- 필수: 단계 4~6개 + 되돌림 연결(`style: dashed`) 1개 이상.
- 배치: 주 흐름은 가로 한 줄 또는 원형. 되돌림은 아래쪽 공통 버스 하나로 모아 선 교차를 줄인다.
- 하단 목표 문장(takeaway)을 둘 수 있다.

### swimlane (그림 예: 재무부·공학과·사업부·PMC·구매생산부)
- 필수: `groups`(kind `lane`) 2~6개, 모든 노드가 레인 하나에 속한다, 시작 노드 1개, 끝 노드 1개 이상.
- 배치: 레인 방향은 단계 수가 많은 축을 따라 정한다(세로 레인 + 위→아래 흐름이 기본). 레인 머리글은 고정 위치. 레인을 넘는 화살표는 직각 경로로 꺾는다.
- decision 노드에서 나가는 연결은 모두 라벨(OK/NG 등)을 단다. 되돌림은 점선.
- 레인 배경은 흰색과 `#F5F5F7`을 번갈아 쓰거나 얇은 구분선만 쓴다. 레인마다 다른 색으로 칠하지 않는다.

### timeline
- 필수: `milestone` 노드 3~8개, 각 노드에 `date`.
- 배치: 가로 축 하나, 시점 간격은 실제 간격에 비례하거나 등간격임을 명시. 라벨은 축 위아래로 번갈아 두어 겹침을 피한다. 현재 시점 표시는 선택.

### comparison (그림 예: OLD/NEW 4열 인포그래픽)
- 필수: 비교 항목 2~5개(`groups` kind `column`), 대비하는 두 쪽(`groups` kind `row`, id 2개), 모든 카드 노드에 `column`·`row` 필드, `contrast_mode`.
- `contrast_mode`로 두 쪽의 관계를 정한다.

| contrast_mode | 두 쪽 | 연결 | 예 |
| --- | --- | --- | --- |
| `before_after` | 시간상 이전 → 이후 | 방향 있는 화살표, 라벨 선택 | OLD → NEW, 2024 → 2025 |
| `same_time` | 같은 시점의 두 면(성과/한계, 겉/속, 큰 값/작은 값) | 방향 없는 대비선(`undirected: true`) + "반면/하지만" 같은 대비 라벨 | 시험 점수 vs 실제 약점 |

- `same_time`에서 위·아래를 화살표로 잇지 않는다. 화살표는 인과("위가 아래를 일으킨다")로 읽힌다. 원문이 인과를 말할 때만 `before_after` 또는 별도 라벨을 쓴다.
- 행 이름은 다섯 열 모두에 맞는 말이어야 한다. 한 열이라도 어긋나면 행 이름을 넓히지 말고 카드 꼬리표(`tag`)로 각 카드의 성격을 적는다.
- 배치: 열 = 항목, 행 = 두 쪽. 한쪽은 중립색, 다른 쪽(또는 focal)만 강조색 계열.
- 각 카드: 머리글(항목명) + 핵심어(굵게) + 보조 설명 + 선택적 아이콘. 아이콘은 기하 도형 수준으로 단순하게.
- 열이 4개 이상이고 카드 본문이 3줄을 넘으면 1600×900에서 넘치기 쉽다. [visual-system.md](visual-system.md)의 열 수별 폭 표로 확인하고, 넘치면 세로 1200×1800(항목 = 행, 두 쪽 = 열)을 distiller 단계에서 고른다.

### architecture (그림 예: claude code → supabase/github/vercel, 내 PC 파일)
- 필수: 층 또는 영역 `groups`(kind `layer`/`zone`) 2~4개, 구성요소 노드, 연결마다 라벨(무엇이 오가는지).
- 배치: 사용자·입력은 왼쪽 또는 위, 외부·클라우드는 위, 로컬·저장소는 아래. 같은 층의 노드는 같은 높이·크기.
- 사람 대신 시스템이 하는 일(위임)을 보이려면 해당 연결만 강조색 + 라벨 "대신 실행"처럼 의미를 적는다. 노란 선처럼 대비 낮은 색은 쓰지 않는다.

### hub-spoke
- 필수: 중심 노드 1개, 주변 노드 3~8개, 각 연결 라벨.
- 배치: 중심은 캔버스 중앙 또는 왼쪽 1/3, 주변은 등각 또는 오른쪽 열. 주변끼리 연결은 최소화.

### decision
- 필수: 시작 1개, decision 노드마다 나가는 연결 2개 이상 + 라벨, 모든 경로가 끝 노드에 도달.
- 배치: 위→아래. 예(Yes) 경로를 직선 주 흐름으로, 예외 경로를 옆으로 뺀다.

## 대비형 쏠림 막기

원문이 "A지만 B" 문장으로 쓰여 있으면(보고서 하이라이트, 회고 등) 모든 그림이 comparison으로 끌려가기 쉽다. comparison을 고르기 전에 확인한다.

1. 결론이 대비 자체인가, 아니면 대비를 거쳐 흐름·시간·구조·책임을 말하는가. 후자면 그 유형이 주인이고 대비는 한 요소(점선 하나, 주석 하나)로 얹는다.
2. 같은 원문 묶음에서 이미 comparison이 절반을 넘었으면, 이번 그림은 차선 유형으로 그릴 수 있는지 근거와 함께 `01_story.md`에 적는다. 그래도 comparison이 낫다면 그 이유를 쓴다.
3. 대비 쌍이 원문에서 직접 짝지어진 것인지, 내가 묶은 것인지 표시한다. 묶은 짝은 `assumed`에 올린다.

## 공통 금지

- 의미 없는 장식 아이콘, 3D, 그림자 남용, 그라데이션 배경.
- 한 그림에 유형 두 개를 대등하게 섞기.
- 모든 노드를 다른 색으로 칠하기.
- 범례가 필요한 색 체계. 직접 라벨로 해결한다.
