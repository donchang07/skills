# To PRD Equip — 장비 소프트웨어용 bkit 실행 계약 작성기

> 상태: 초안 v0.1 · 원본: `to-prd` (screen-first-v2) · PRD 스키마: change-area-v1

이 스킬은 `to-prd`의 운영 방식(정본 하나, ID 보존, 비목표, 착수 게이트, 두 관문, `CLAUDE.md` 실행 규칙)을 그대로 쓰고, **화면 계약 자리를 변경 영역 계약으로 바꾼** 장비 소프트웨어용 변형판이다.

품질 기준은 하나다.

> 이 PRD만 받은 bkit이 어느 고객·장비·기준 버전에서, 어떤 변경 영역의 어떤 항목을 어떻게 바꾸고, 어디는 절대 건드리지 않으며, 어떤 골든 이미지와 호스트 시나리오로 회귀 없이 완료를 판정할지 알 수 있다.

## 왜 별도 스킬인가

장비 소프트웨어 업그레이드의 대부분은 화면이 없는 변경이다. 검사 기능 변경(검사 기준·레시피·불량 분류)과 호스트 연동 변경(SECS/GEM 메시지·이벤트·알람, E84/E87 상태 전이)을 `to-prd`로 돌리면 핵심 항목이 모두 `해당 없음 — 이유`로 빠진 채 게이트를 통과한다. 이 스킬은 그 항목을 1급 계약으로 다룬다.

| to-prd (웹) | to-prd-equip (장비) |
|---|---|
| 화면 인벤토리 `SCR-*` | 변경 영역 인벤토리: `RCP`·`INS`·`DEF`·`HOST`·`LOG`·`UI` |
| UI 요소 `SCR-001-EL-01`, `DATA-*` | 영역 항목의 파라미터·메시지·변수(SVID·CEID·ALID·ECID) |
| 화면 상태 8종 | 장비 상태: 제어 상태(E30)·처리 상태·통신 상태·알람·캐리어(E87) |
| 역할(비로그인·일반·관리자) | 장비 권한 레벨(운영자·엔지니어·유지보수)과 호스트 |
| `[E2E]` Playwright | `[골든]` 이미지 재생 · `[가상호스트]` · `[HIL]` · `[단위]` · `[현장]` |
| `data-testid` | 요구사항 ID ↔ 코드 ↔ 시험 추적표 |
| 비목표 `NG-*` | 비목표 `NG-*` + **동결 영역 `FRZ-*`**(AI 수정 금지) |
| 두 관문 | **세 관문**: match rate · 시험 통과 · 범위 감시 |
| 정본 하나 | 제품 정본 + 고객 정본의 **2층 정본** |

## 운영 불변식

1. **정본은 층마다 하나다.** 제품 공통은 `docs/PRD.md`, 고객별 차이는 `docs/customers/{customer}/PRD.md`가 정본이다. 고객 정본은 제품 정본의 개정 번호를 메타에 고정해 참조하고, 제품 정본의 내용을 복사하지 않는다. feature 파생본은 두 정본에서 생성한다.
2. **feature 파생본을 직접 편집하지 않는다.** 파생본에만 있는 사람의 편집은 해당 층의 정본으로 옮긴다.
3. **변경 영역 계약이 FR보다 먼저다.** 장비·기준 버전 → 동결 영역 → 변경 영역 항목 → 장비 상태 → FR·SC 순서로 쓰고 양방향 연결을 검증한다.
4. **동결 영역은 PRD로 바꾸지 않는다.** `FRZ-*`에 있는 모듈은 FR의 대상이 될 수 없다. 바꿔야 하면 PRD 밖에서 사람이 별도 절차로 바꾸고, PRD에는 그 결과만 기준 버전으로 반영한다.
5. **기준 버전이 없으면 증분도 없다.** 고객 정본은 현장 소프트웨어의 기준 버전(태그·커밋)과 허용 변경 경로를 가진다. 증분은 이 기준에서만 계산한다.
6. **개정 번호는 `vX.Y`, ID는 재사용하지 않는다.** `to-prd`와 같다. 삭제는 취소선과 사유로 남긴다.
7. **Hard Gate가 점수보다 우선한다.** Blocker가 있으면 draft로만 저장한다.
8. **고객 데이터는 고객 보안 등급을 따른다.** 골든 이미지·통신 로그·고객 사양서의 위치와 반출 가능 여부를 11.2에 쓰고, 반출 불가 데이터는 경로와 해시만 PRD에 남긴다. 실제 이미지나 사양서 원문을 PRD에 붙이지 않는다.
9. **bkit 버전 계약은 `references/bkit-contract.md`에서만 관리한다.**

## Step 0 — bkit 계약 확인

`to-prd`와 같다. `references/bkit-contract.md`를 읽고 로컬 설치본과 `bkit.config.json`을 우선한다.

## Step 1 — 모드 판단

- **신규 장비 모드:** 기존 소스가 없거나 새 제품이다. 제품 정본부터 쓴다. 기준 버전은 공통 코어의 태그다.
- **고객 변경 모드:** 고객 변경 요청서가 있다. 고객 정본이 있으면 업데이트, 없으면 고객 정본을 새로 만든다.
- **역생성 결합 모드:** 고객 정본이 없고 `code-prd-equip`의 `_as-is/{customer}.md`가 있다. `AS-*` ID는 PRD ID로 새로 부여하고 as-is 문서 7장에 대응을 남긴다. `[역추출·확인]` 항목은 현재 값으로 쓰고, `[역추출·정정]`은 정정 값을 쓴다. 역추출 항목을 고객 정본의 현재 값으로 옮기되 `[역추출]` 라벨을 유지한다. 이번 변경이 건드리는 `[역추출]` 항목은 핵심 개발자 확인 전까지 Blocker다(HG-E09).
- 업데이트는 해당 층의 정본을 먼저 고치고 영향받는 파생본을 모두 재생성한다. 제품 정본이 바뀌면 그 개정을 참조하는 고객 정본 목록을 보고에 남긴다(자동 갱신하지 않는다).

## Step 2 — 입력 매핑

`references/request-mapping.md`를 읽고 대응표대로 옮긴다. 필수 항목(고객·장비·기준 버전, 변경 영역, 요청 내용, 수용 기준, 시험 데이터 확보 여부)이 비었으면 객관식으로 묻는다. 최대 4문항, 2회 이내.

작업 메모로 다음 표를 만든다.

1. 고객·장비 모델·대수·현장 기준 버전·보안 등급
2. 요청 → 변경 영역 → 영역 항목 → 바뀌는 값(현재 → 목표)
3. 영역 항목 → 영향 받는 모듈 경로 → 허용 변경 경로
4. 영역 항목 → 동결 영역과의 경계 → 경계를 넘는지 여부
5. 영역 항목 → 장비 상태별 동작
6. 영역 항목 → FR → SC → 시험 수단과 시험 데이터
7. 이번에 만들지 않을 것(NG)과 동결 영역(FRZ)
8. AI 기능(불량 분류 등)이 있으면 AI 결과와 사람 확정값

## Step 3 — 장비·시험·시스템 가정

FR을 쓰기 전에 11장을 채운다.

- **장비·기준:** 장비 모델, 제품군, 현장 소프트웨어 기준 버전(태그·커밋), 개발 언어·빌드 명령. 모르면 13장 결정 요청이며 Blocker다(HG-E05).
- **시험 체계(11.1):** 시험 수단별 실행 명령 한 줄씩. `[단위]` 명령, `[골든]` 재생 명령과 골든셋 ID·버전, `[가상호스트]` 시나리오 명령과 시나리오 ID, `[HIL]` 사용 여부. 가상 팹이 아직 없는 단계면 `[골든]`·`[가상호스트]`를 `[현장]`으로 대체하지 말고 13장 결정 요청과 fallback(해당 변경 보류 또는 사람 검증 범위 축소)을 둔다.
- **시스템 가정 10칸(11.2):** 아래 칸을 모두 채운다. 상태 라벨은 to-prd와 같다(`[확정]`·`[기본값]`·`[해당 없음]`·`[결정 필요]`).

| # | 칸 |
|---|---|
| 1 | 고객·장비·현장 기준 버전 |
| 2 | 고객 보안 등급과 데이터 반출 범위(A·B·C) |
| 3 | 골든 이미지셋 출처·버전·사용 동의 |
| 4 | 호스트 사양 문서(GEM 매뉴얼 등)와 버전 |
| 5 | 적용 SEMI 표준과 버전(E5·E30·E37·E40·E84·E87·E90·E94 등) |
| 6 | 장비 하드웨어 구성과 HAL 경계 |
| 7 | 배포·롤백 방식과 설치 창 |
| 8 | 호스트·외부 장치 장애 시 동작 |
| 9 | 처리량·타이밍 기준(UPH·tact·응답 시간) |
| 10 | 수치·외부 사실 출처와 기준일 |

## Step 4 — 변경 영역 계약 작성

`references/change-area-contract.md`를 읽고 이 순서로 쓴다.

1. **동결 영역(5.1):** `FRZ-*` ID, 모듈·경로, 이유, 변경 시 절차. 제품 정본에서 정의하고 고객 정본은 참조만 한다. 고객 정본은 고객 특이 동결 항목만 추가할 수 있다.
2. **변경 영역 인벤토리(5.2):** 이번 범위의 항목을 영역 코드별 ID로 나열한다. `RCP-001`, `INS-001`, `DEF-001`, `HOST-001`, `LOG-001`, `UI-001`.
3. **영역별 상세(5.3~5.7):** 영역마다 정해진 표를 쓴다. 현재 값과 목표 값, 근거 문서, 허용 변경 경로를 반드시 가진다.
4. **장비 상태 매트릭스(5.8):** HOST·LOG·UI 항목이 각 제어·처리·통신 상태와 알람에서 어떻게 동작하는지.
5. **권한(5.9):** 운영자·엔지니어·유지보수·호스트별로 항목을 보고 바꿀 수 있는지.
6. **FR·SC(6~7장):** 영역 항목의 변경에서 FR을 도출한다. FR은 영역 항목 ID와 허용 경로를 가진다. SC의 측정 방법은 시험 수단 라벨로 시작한다.
7. **증분 계약(5.10):** 기준 버전, 허용 변경 경로 목록, 예상 변경 규모, 롤백 방법. bkit이 이 경로 밖을 고치면 세 번째 관문에서 실패한다.

시험 수단 규칙(자세한 것은 contract 8절):

- 판정 결과를 바꿀 수 있는 `RCP`·`INS`·`DEF` 변경 → `[골든]` SC 필수. 기대 판정 일치율과 허용 차이를 쓴다.
- `HOST`·`LOG` 변경 → `[가상호스트]` SC 필수. 메시지 순서·내용과 상태 전이를 판정한다.
- 타이밍·모션 연동이 바뀌면 `[HIL]`. HIL 환경이 없으면 13장 결정 요청.
- `[현장]`은 사무실에서 재현할 수 없는 이유를 함께 쓴다. P0 SC 전체가 `[현장]`이면 Blocker다(HG-E10).

## Step 5 — 정본 구성과 feature 분해

`assets/prd-template.md`를 따른다. feature는 한 번의 PDCA와 한 번의 골든·가상호스트 회귀로 검증할 수 있는 크기로 자른다. 한 feature가 서로 다른 영역(예: INS와 HOST)을 함께 바꾸면 의존 순서를 14장에 쓴다.

## Step 6 — 착수 게이트

`references/gate-checklist.md`대로 `scripts/validate_prd.mjs`를 정본과 파생본에 실행하고 Hard Gate·점수를 판정한다. 판정 기준은 to-prd와 같다(착수 가능: Blocker 0·90점 이상, 조건부: Blocker 0·70~89점, 착수 불가: 그 외).

## Step 7 — 저장과 동기화

게이트를 통과하면 정본·파생본·gate·decisions를 저장하고 `CLAUDE.md`의 블록을 정본에서 다시 생성한다. 마커 밖은 고치지 않는다.

```markdown
<!-- to-prd-equip:begin — PRD에서 생성됨. 직접 고치지 말고 PRD를 갱신한 뒤 to-prd-equip을 다시 실행할 것 -->
## to-prd-equip 실행 규칙

- 요구사항 정본: 제품 `docs/PRD.md`({제품 개정}) · 고객 `docs/customers/{customer}/PRD.md`({고객 개정}). feature 기준은 `docs/00-pm/{customer}-{feature}.prd.md`다.
- 기준 버전은 `{태그·커밋}`이다. 증분은 이 기준에서만 만든다.
- 허용 변경 경로: `{경로 목록}`. 이 밖의 파일은 수정하지 않는다. 필요해 보이면 구현하지 말고 PRD 갱신을 요청한다.
- 동결 영역(FRZ-*): `{경로 목록}`. 읽기만 한다. 수정·리팩터링·포맷 변경도 하지 않는다.
- PRD 3장 비목표(NG-*)는 구현하지 않는다.
- 코드 변경마다 관련 FR ID를 커밋 메시지와 추적표에 남긴다.
- `/pdca analyze`(Check) 단계에서 다음 명령을 실제로 실행하고 결과를 analysis 문서에 기록한다: `{단위}` · `{골든}` · `{가상호스트}`
- 완료는 세 관문이다: match rate {기준}% 이상, 위 시험 전체 통과, 기준 버전 대비 변경 파일이 모두 허용 경로 안이고 동결 영역 변경 0건. 하나라도 실패하면 `/pdca report`로 넘어가지 않는다.
<!-- to-prd-equip:end -->
```

착수 불가면 draft 경로에만 저장하고 `CLAUDE.md` 블록은 갱신하지 않는다. 저장 여부를 묻지 않는다.

## Step 8 — 보고

고객대응 엔지니어와 핵심 개발자가 읽는다. 순서:

1. 저장한 정본·draft 경로, `CLAUDE.md` 블록 갱신 여부
2. 게이트 판정과 Blocker/Major/Minor 수
3. 결정 요청 번호·선택지·추천(특히 기준 버전, 골든셋, 호스트 사양)
4. 동결 영역과 맞닿은 항목, `[역추출]`로 남은 항목
5. feature 분해와 첫 실행 명령 `/pdca plan {customer}-{feature}`
6. 고객에게 다시 확인할 사양

## 원칙

- **소스를 직접 역생성하지 않는다.** 기존 소스의 현재 상태는 `code-prd-equip`이 추출한다.
- **장비 소프트웨어 전용이다.** 웹·모바일 앱은 `to-prd`를 쓴다. 장비 주변의 웹 도구(가상 팹 대시보드 등)도 `to-prd`다.
- **바꿀 곳보다 바꾸지 않을 곳을 먼저 고정한다.** 동결 영역과 허용 경로가 없는 PRD는 완료된 계약이 아니다.
- **증분은 기준 버전에서만 계산한다.**
- **판정을 바꾸는 변경은 골든 이미지로, 통신을 바꾸는 변경은 가상 호스트로 검증한다.**
- **고객 데이터는 PRD에 붙이지 않는다.** 경로·버전·해시만 쓴다.
- **`[역추출]` 값은 확인 전까지 사실이 아니다.**
- **추측을 숨기지 않는다.** `[확정·출처]`·`[조사·기준일]`·`[추정]`·`[가설]`·`[역추출]`을 구분한다.
- **ID와 개정 이력을 보존한다.**
