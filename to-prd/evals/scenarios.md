# 실행 시나리오와 검증 조건

to-prd를 고친 뒤 다음 시나리오를 빈 프로젝트 폴더에서 실행해 확인한다. 같은 요청을 이 스킬 없이 실행한 기준 결과와 나란히 비교하면 개선 폭을 볼 수 있다. 검증 조건은 참·거짓을 객관적으로 가릴 수 있는 것만 쓴다. 기준 실행도 언제나 통과하는 조건(예: "PRD 파일이 있다")은 개선을 측정하지 못하므로 넣지 않는다.

공통 확인: `node scripts/check_output.mjs <프로젝트>`가 통과하고, 정본에 `node scripts/validate_prd.mjs`가 ERROR 0이다(draft 시나리오 제외).

## S1 정상 — `briefs/normal.md`

요청: `/to-prd evals/briefs/normal.md로 bkit용 PRD 만들어줘`

| 검증 조건 | 확인 방법 |
|---|---|
| 작성 모드가 Lean이다(로그인·예약 현황·승인함 3개 화면, 업무 역할 2개, AI·외부 연동 없음) | 정본 메타 `작성 모드: Lean` |
| 근거가 적힌 규정(중복 금지 3조, 1년 보존)은 `[확정·출처]`, 목표 일정은 임의 날짜가 아니다 | 정본 검색 |
| NG-001 외부 손님 예약, NG-002 반복 예약이 있고 캘린더 연동은 10장 이후 범위다 | 3장·10장 |
| G-001이 "중복 예약 주 15건 → 0건, 사용 4주 후, 총무팀장"을 담는다 | 3장 성공 지표 표 |
| 11.4~11.6이 `해당 없음 — 브리프 4장`이고 15장은 두 관문이다 | 11장·15장 |
| gate 파일에 독립 검토자 2명 이상 또는 `단일 세션 역할 전환`이 기록된다 | `_product.gate.md` |

## 호출 조건

`triggers.json`의 should_trigger 10개는 to-prd를, should_not_trigger 10개는 `better`에 적힌 스킬이나 직접 답변을 불러야 한다. description을 고쳤으면 다시 확인한다.

## 회귀 기준

- `examples/sample-prd.md`에 `validate_prd.mjs`를 실행하면 ERROR 0, WARN 0이다. 검사기를 고친 뒤 이 결과가 바뀌면 검사기 회귀다.
- 실행 결과가 S1~S5 가운데 하나라도 나빠지면 그 변경은 되돌리거나 원인을 원리 수준에서 고친다. 사례 하나에 규칙 하나를 붙이지 않는다.
