# 화면 정의 계약

화면 정의는 PRD의 부록이 아니라 Functional Requirements와 데이터 계약의 입력이다. 화면을 먼저 확정하지 않은 상태에서 FR이나 데이터 모델을 완성했다고 판정하지 않는다.

## 1. 작성 순서

1. 사용자 역할과 접근 권한을 정한다.
2. 화면 인벤토리와 사이트맵을 만든다.
3. 데스크톱·모바일 메뉴와 화면 전이를 정한다.
4. 로그인·로그아웃·세션 만료·접근 거부 흐름을 정한다.
5. 각 화면의 영역과 UI 요소를 정의한다.
6. 각 요소의 표시 데이터, 입력 규칙, 행동 결과를 연결한다.
7. 화면과 요소에서 `DATA-*`, `FR-*`, `SC-*`를 도출한다.
8. 생성한 ID를 화면 계약에 다시 연결해 양방향 추적성을 완성한다.

기존 PRD를 업데이트할 때는 화면 순서 번호를 참조 키로 사용하지 않는다. 기존 화면에 `SCR-001`부터 안정적인 ID를 부여하고, 삭제된 ID는 재사용하지 않는다. UI 요소는 화면에 종속된 `SCR-001-EL-01` 형식을 사용한다.

## 2. 역할과 버전 차이

최소 역할은 `비로그인`, `일반 사용자`, `관리자`다. 제품에 특정 역할이 없더라도 열을 삭제하지 않고 `해당 없음 — 이유`를 쓴다.

일반 버전과 관리자 버전의 차이는 다음 위치에서 모두 보여야 한다.

- 역할·접근 매트릭스: 볼 수 있는 정보와 실행할 수 있는 기능
- 화면 인벤토리: 역할별 접근 가능한 화면
- 메뉴·내비게이션: 역할별 메뉴 노출과 순서
- 화면별 레이아웃: 같은 영역의 표시·편집 차이
- UI 요소 계약: 요소별 노출 권한과 활성 조건
- 상호작용 표: 관리자 작업의 저장·감사·실패 결과

레이아웃이나 작업 흐름이 크게 다르면 일반 화면과 관리자 화면을 별도 `SCR-*`로 만든다. 같은 화면에서 버튼이나 패널만 달라지면 하나의 화면 안에서 역할별 차이를 명시한다.

## 3. 메뉴와 내비게이션

메뉴 표에는 다음을 빠뜨리지 않는다.

- `NAV-*` ID
- 위치와 표시 순서
- 실제 라벨
- 노출 역할
- 이동할 `SCR-*`
- 데스크톱 표현
- 모바일 표현
- 현재 위치의 활성·선택 규칙

헤더, 사이드바, 하단 탭, 프로필 메뉴, 관리자 메뉴를 구분한다. 메뉴에 없는 진입점은 딥링크, 카드, 버튼, 알림 등 실제 진입 방법을 화면 인벤토리에 기록한다. 뒤로 가기와 취소 시 복귀 위치도 화면별 종료·전이에 쓴다.

## 4. 인증과 권한 화면

관리자 기능이나 보호된 데이터가 하나라도 있으면 `인증 사용: 예`다. 이 경우 로그인 또는 인증 시작 화면을 독립된 `화면 유형: 인증` 화면으로 정의한다. 인증 방식에 필요한 경우 다음도 별도 화면 또는 명시적인 화면 상태로 정의한다.

- 인증 결과·콜백
- 잘못되거나 만료된 링크
- 접근 권한 없음
- 로그아웃
- 세션 만료와 원래 화면 복귀

로그인 화면도 다른 화면과 같은 수준으로 Route, 입력 필드, 검증, 버튼, 성공 전이, 실패 문구, 로딩·오류 상태, 데이터 처리를 정의한다. 인증을 사용하지 않으면 `인증 사용: 아니오 — 이유`와 관리자·보호 기능이 없다는 근거를 남긴다.

## 5. 화면별 필수 계약

각 `SCR-*`에는 다음이 있어야 한다.

### 메타데이터

- 화면 유형: `공개`, `일반`, `관리자`, `인증`, `공통` 중 하나
- Route 또는 route가 없는 UI라면 실제 진입 방식
- 대상 사용자와 읽기·쓰기 권한
- 화면의 단일 목적
- 진입 조건
- 성공·취소·뒤로 가기의 종료와 전이
- 관련 시나리오, FR/SC, 데이터

### 레이아웃·영역

헤더, 메뉴, 본문, 사이드바, 패널, 모달, 푸터 등 화면 안의 영역을 위에서 아래 또는 왼쪽에서 오른쪽 순서로 기록한다. 각 영역에서 사용하는 요소 ID와 일반 사용자·관리자 차이, 모바일 재배치를 함께 쓴다.

### UI 요소 계약

각 요소는 다음 열을 가진다.

| 열 | 의미 |
|---|---|
| 요소 ID | `SCR-001-EL-01` 형식의 안정적인 ID |
| 종류 | 제목, 텍스트, 입력, 선택, 버튼, 카드, 표, 지도, 모달 등 |
| 표시 내용·라벨 | 화면에 실제로 보일 정보 또는 카피 |
| 사용자·권한 | 볼 수 있거나 사용할 수 있는 역할 |
| 표시·활성 조건 | 언제 보이고 활성화되는지 |
| 데이터 바인딩 | `DATA-001.field`, `정적`, 또는 `해당 없음 — 이유` |
| 입력·검증 | 타입, 필수 여부, 기본값, 범위, 형식, 오류 문구 또는 읽기 전용 |
| 행동·결과 | 클릭·변경 시 처리, 저장 여부, 피드백과 다음 화면 |

“버튼”, “목록”처럼 이름만 적는 것은 화면 정의가 아니다. 사용자가 보는 값, 누를 때 일어나는 일, 필요한 데이터가 모두 있어야 한다.

### 상호작용·전이

트리거, 선행 조건, 처리와 데이터 변화, 성공 결과·다음 화면, 실패 결과, 관련 FR/SC를 기록한다. 생성·수정·삭제·로그인 같은 쓰기 동작은 중복 실행 방지와 감사 또는 로그 정책도 포함한다.

### 화면 상태

각 화면은 아래 상태를 모두 다룬다. 적용되지 않으면 이유를 쓴다.

- 초기
- 로딩
- 빈
- 성공
- 검증 오류
- 시스템 오류
- 권한 없음
- 오프라인

상태마다 트리거, 보이는 요소와 문구, 가능한 행동, 복구·다음 전이를 적는다.

### 반응형·접근성

모바일·태블릿·데스크톱에서 메뉴와 주요 영역이 어떻게 바뀌는지, 키보드 순서·포커스·라벨·대비·터치 영역 같은 적용 기준을 쓴다.

## 6. 화면에서 FR과 데이터 도출

- 사용자 행동이나 시스템 반응이 구현되어야 하면 `FR-*`로 만든다.
- 동적 표시값이나 사용자 입력은 `DATA-*` 엔티티·필드에 연결한다.
- 정적 카피와 장식 요소는 데이터 계약에서 제외할 수 있지만 `정적`이라고 명시한다.
- 화면 없는 배치·연동·운영 요구는 `화면·요소`에 `해당 없음 — 이유`를 쓰고 별도 FR로 유지한다.
- 한 UI 요소가 어떤 FR에도 연결되지 않으면 장식·정적 정보인지 확인하고, 그렇지 않으면 FR 누락이다.
- 한 P0 FR이 화면 동작을 요구하면서 `SCR-*` 또는 요소 ID가 없으면 Blocker다.
- 화면에서 참조한 `DATA-*`가 부록 A에 없거나, 부록 A 필드가 어떤 화면·FR에도 쓰이지 않으면 결함이다.

## 7. feature 파생본

feature PRD에는 해당 feature가 소유하는 화면과 요소 계약을 원문 의미 그대로 포함한다. 공통 메뉴·인증·권한 계약이 feature 동작에 영향을 주면 관련 행과 화면도 함께 포함한다. 정본과 파생본에서 같은 `SCR-*`, 요소 ID, `DATA-*`, `FR-*`, `SC-*`를 사용한다.
