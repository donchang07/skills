# 업무 브리프 → PRD 대응 계약

> 브리프 버전: v1.4
> 템플릿: `assets/brief/PRD템플릿_v1.4.docx`
> 핸드북: `assets/brief/PRD작성핸드북_v1.4.docx`
> PRD 스키마: screen-first-v3

템플릿·핸드북·to-prd는 한 묶음이다. 어느 하나를 바꾸면 세 곳의 버전을 함께 올리고 `node scripts/check_sync.mjs`로 확인한다.

## 1. 읽기

1. Word 브리프는 `pandoc -t markdown <파일>`로 읽는다. pandoc이 없으면 `python-docx`로 문단과 표를 읽는다. 둘 다 안 되면 사용자에게 내용을 붙여 넣어 달라고 한다.
2. 브리프 파일 속성 제목(`to-prd를 사용하기 위한 PRD 템플릿 vX.Y`) 또는 파일명의 버전이 이 문서의 브리프 버전과 다르면 PRD 메타 `입력`에 차이를 기록하고, 아래 대응표에 없는 항목은 가장 가까운 장으로 옮긴다.

## 3. 화면 상태 도출

템플릿은 업무에 필요한 예외만 입력받는다. to-prd가 화면마다 초기·로딩·빈·성공·검증 오류·시스템 오류·권한 없음·오프라인의 적용 여부와 동작을 도출한다. AI 결과를 보여 주는 화면에는 `AI 판단 보류`를 더한다. 취소·반려·이탈은 실패 시나리오와 Edge Cases에 반영한다. 입력에 없는 구현·디자인·테스트 기본값을 현업에게 미리 작성시키지 않는다.

## 4. 모름과 추천값 적용

| 브리프 값 | 필수 항목 | 그 밖의 항목 |
|---|---|---|
| 내용 있음 | `[확정·출처: 업무 브리프 vX.Y]`. 단, 아래 확정 판정을 먼저 적용 | 같음 |
| `(추정)` 표시 | `[추정]` + 13장 확인 요청 | `[추정]` |
| 추천값 적용 | `[기본값]` + 13장 확인 요청 | `[기본값]` |
| 모름 또는 빈칸 | 객관식 질문 (5절) | `[기본값]`, P0 아키텍처가 달라지면 13장 결정 요청 |

**확정 판정.** 작성자 본인의 업무 경험(현재 불편, 업무 순서)은 내용이 있으면 확정이다. 금액·정책·법규·승인 단계·보존 기간·화면 수·역할 수처럼 뒤집히면 아래 문서까지 연쇄 수정되는 값은 근거(규정 이름·문서·결정한 사람)가 함께 적혀 있을 때만 확정이다. 근거가 없으면 `[추정]`으로 두고 13장 `D-*` 하나에 묶어 확인을 요청한다.

PRD 작성에 필요한 핵심 항목은 다음과 같다: **업무 문제, 사용자, 현재와 미래 흐름, 필요한 화면, 예외, 완료 기준과 반드시 통과해야 할 사용자 흐름**.

## 5. 필수 항목 객관식 질문

필수 항목이 비었거나 모름일 때만 묻는다. 한 번에 최대 4문항, 전체 2회 이내다. Claude Code에서는 AskUserQuestion을 쓰고, 그 도구가 없는 환경(Codex 등)에서는 같은 객관식을 번호 목록으로 묻는다. 첫 선택지를 `(추천)`으로 둔다. 선택지는 브리프의 업무 이름으로 구체화한다. 질문에 SCR·FR·SC·P0·Route·DATA·E2E·스택·PDCA를 쓰지 않는다.

| 필수 항목 | 질문 | 무응답 시 |
|---|---|---|
| 업무 문제 | 이 앱이 없애려는 불편은 무엇인가요? (브리프 맥락에서 2~4개) | 중단 — 업무 문제 없이는 PRD를 만들지 않음 |
| 사용자 | 이 앱은 누가 쓰나요? ① 팀원 + 관리 담당자 따로 (추천) ② 팀원만 ③ 나 혼자 ④ 외부 고객·협력사까지 | ① `[기본값]` + 13장 |
| 현재와 미래 흐름 | 앱을 쓴 뒤 일이 어떤 순서로 바뀌나요? (브리프에서 만든 흐름 후보 2~3개) | 첫 후보 `[기본값]` + 13장 |
| 필요한 화면 | 첫 버전에 꼭 있어야 하는 화면을 모두 고르세요. (복수 선택) | 흐름에서 도출 `[기본값]` + 13장 |
| 예외 | 자주 생기는 예외를 모두 고르세요. ① 반려·취소 ② 데이터 없음 ③ 외부 시스템 응답 없음 ④ 통신 끊김 (복수 선택) | ①② `[기본값]` + 13장 |
| 반드시 통과해야 할 사용자 흐름 | 이것만은 반드시 끝까지 되어야 하는 흐름은? (미래 흐름에서 만든 후보 2~3개, 복수 선택) | 미래 흐름 첫 후보를 `[E2E]` SC `[기본값]` + 13장 |
| AI 품질 기준 (AI를 쓸 때만) | AI 답이 어느 정도면 쓸 만한가요? ① 실제 규정·자료와 맞는 답 90% 이상 (추천) ② 95% 이상 ③ 사람이 매번 확인하므로 80% 이상 / 절대 하면 안 되는 것도 고르세요(복수 선택): 근거 없는 약속, 개인정보 요구, 규정 밖 판단 | ① + 금지 행동은 선택지 전체, `[기본값]` + 13장 |
| 완료 기준 | 무엇이 되면 성공인가요? ① 처리 시간이 줄어든다 (추천) ② 빠뜨리는 건이 없어진다 ③ 입력 실수가 줄어든다 ④ 보고서를 따로 만들 필요가 없다 | ① + 목표값 `[가설]` + 13장 |

답변은 `[확정·출처: 현업 응답 YYYY-MM-DD]`로 반영하고 `docs/00-pm/_interview.md`에 `날짜 / 문항 / 선택 / 반영 위치 / 상태`로 기록한다. 업데이트 때 같은 질문을 다시 하지 않는다. 무인 실행이면 묻지 않고 무응답 열을 적용한다.

## 6. 비목표

- 템플릿 3장 "이번에 제외할 것과 이유"의 각 항목이 NG-*가 된다. 3장 "나중에 추가할 것"은 비목표가 아니라 10장 이후 범위다.
- 다시 검토할 시점이 없으면 `[기본값] 다음 버전 기획 시`로 쓴다.
- 브리프에 비목표가 없으면 브리프에서 언급됐지만 MVP에서 뺀 기능을 `[기본값]` 비목표로 제안하고 13장에 확인 요청을 둔다.

## 7. AI 계약

템플릿 4장 "AI를 사용하는 경우"에 AI 기능이 명시되면 PRD 11.4~11.6을 채운다. AI를 쓰는데 "AI가 잘했다고 볼 기준"이나 "AI가 절대 하면 안 되는 것"이 비어 있으면 5절 AI 품질 기준 질문을 한다.

### 11.4 판정 계약

- AI 기능별로 입력, 출력, 사람이 확정하는 주체와 화면, 반드시 사람이 확인할 조건, AI가 틀렸을 때 되돌리는 방법, AI 실패 시 동작을 쓴다.
- 부록 A에서 AI 결과 필드와 사람 확정 필드를 다른 필드로 둔다. 확정자·확정 시각·AI와 다를 때의 사유 필드를 포함한다.
- 확정, 사람 확인 조건, 되돌리기는 FR로 만들고 `[E2E]` SC로 검증한다. AI 모델 응답은 테스트에서 모킹한다.

### 11.5 품질 평가

- `EV-*`마다 AI 기능, 유형(품질·금지), 기준, 합격선, 평가 데이터(출처·건수), 평가 방법을 쓴다.
- 품질 기준은 측정 가능한 비율로 쓴다(예: 규정 문서와 대조한 사실 정확도 90% 이상). 측정할 수 없는 기준은 쓰지 않는다.
- 금지 행동은 합격선을 `0건`으로 고정한다. 1건이라도 나오면 평가 불합격이다.
- 평가 데이터는 현업이 준 실제 사례(정답 포함)를 쓴다. 없으면 `[기본값]` 30건을 현업에게 요청하는 13장 결정으로 두고, 준비될 때까지 세 번째 관문은 통과할 수 없다고 적는다.
- 판정 방법은 정답 대조, 근거 문서 대조, 사람 검토 중 하나를 쓴다. 사람 검토면 검토자와 기준을 쓴다.

### 11.6 운영 기준

- 판단 보류: AI가 확신이 없거나 근거가 없을 때의 동작과 사람에게 넘기는 화면. 해당 화면에 `AI 판단 보류` 상태를 둔다.
- 비용: 건당 또는 세션당 비용 상한과 넘었을 때의 알림.
- 응답시간: P95 기준. 브리프에 없으면 `[기본값]` 3초.
- 버전 고정: 모델·프롬프트·참고자료 버전. 바꾸면 평가를 다시 실행한다.
- 운영 감시: 품질 지표와 금지 행동 감지, 측정 주기와 책임자.
- 롤백 조건: 품질 지표가 합격선 아래로 떨어지거나 금지 행동이 1건이라도 감지되면 직전 버전으로 되돌린다. 구현 방식은 12장 구현자 이슈로 둔다.

## 8. 성공 지표

- 템플릿 1장 "원하는 변화"와 6장 "성공을 확인할 기준"이 3장 성공 지표 `G-*`가 된다. 구분 열에 업무 목표(회사·팀이 얻는 것)와 사용자 목표(실제 사용자가 편해지는 것)를 나눈다.
- 각 G-*에 현재값, 목표값, 측정 방법·데이터 출처, 측정 시점, 책임자를 쓴다. 측정 시점이 없으면 `[기본값] 사용 4주 후`, 책임자가 없으면 브리프 작성자로 두고 13장에 확인 요청을 둔다.
- 소프트웨어가 직접 보장하는 조건(예: 처리 화면이 2단계 이내)은 7장 SC로, 업무 결과(예: 처리 시간 단축)는 G-*로 둔다.
- 측정 시점이 지나 사용자가 결과를 주면 `docs/00-pm/_review.md`에 `G-* / 측정값 / 목표 달성 여부 / 원인 / 다음 개정 반영`으로 기록하고 다음 개정 입력으로 쓴다.
