# 독립 검토 팀

PRD를 쓴 쪽이 자기 PRD를 채점하면 자기 해석을 다시 확인할 뿐이다. 그래서 Step 6 게이트는 작성 맥락을 보지 않은 검토자가 판정한다. 이 문서는 검토자의 역할, 실행 방법, 결과 형식, 반복 규칙을 정한다. 구조는 생성·검증 패턴에 관점별 분산 검토, 적대적 확인, 누락 검토를 더한 것이다.

## 목차

1. 역할
2. 작성 모드별 구성
3. 실행 방법
4. 검토자에게 넘기는 입력
5. 결과 형식
6. 적대적 확인
7. 반복과 종료
8. 작업 폴더

## 1. 역할

| 역할 | 보는 것 | 묻는 질문 |
|---|---|---|
| 작성자 | 브리프·기존 정본·대화 | 이 스킬 본체. 정본과 파생본을 쓰고 고친다 |
| 게이트 검토자 | `validate_prd.mjs` 결과, Hard Gate, 연결표 | 기계 검사와 HG-01~HG-15를 통과하는가 |
| 현업 관점 검토자 | 브리프 ↔ PRD | 브리프의 모든 항목이 반영됐는가. 비목표가 지켜졌는가. 근거 없는 확정이 있는가. 0장을 현업이 읽고 동의할 수 있는가 |
| 구현 관점 검토자 | PRD ↔ bkit 계약 | bkit이 추측해야 하는 지점이 있는가. 화면·요소·데이터·FR·SC 연결이 끊긴 곳이 있는가. 정본과 파생본의 의미가 같은가 |
| 검증 관점 검토자 | SC·NFR·11.1·11.5 | 모든 SC를 실제로 판정할 수 있는가. P0 상태가 E2E로 이어지는가. AI가 있으면 평가 데이터·합격선·금지 0건이 측정 가능한가 |
| 누락 검토자 | 앞 검토 결과 전체 + PRD | 다른 검토자가 놓친 것만 찾는다. 이미 나온 결함은 반복하지 않는다 |

연결 지점에서 생기는 결함이 가장 잘 숨는다. 화면 표에는 있는데 FR에 없는 요소, 브리프에는 있는데 PRD에 없는 예외, 정본에는 있는데 파생본에서 빠진 비목표가 그렇다. 그래서 검토자는 한 문서만 읽지 않고 **연결된 양쪽을 함께 열어 대조**한다. "표가 있다"가 아니라 "A의 각 행이 B의 어느 행과 맞는가"를 기록한다.

## 2. 작성 모드별 구성

| 작성 모드 | 검토자 | 적대적 확인 |
|---|---|---|
| 변경 노트 | 게이트 검토자 1명. 바뀐 ID와 그 연결만 본다 | 하지 않음 |
| Lean | 게이트 검토자 + 구현 관점 검토자 | Blocker만 |
| Full | 게이트 검토자 + 현업·구현·검증 관점 검토자 + 누락 검토자 | Blocker와 Major |
| 검토 모드(실행 모드) | Full과 같음. 작성자는 PRD를 고치지 않고 결과만 보고한다 | Blocker와 Major |

검토자가 많을수록 비용과 시간이 늘어난다. 사용자가 "꼼꼼히", "전수"처럼 넓은 검토를 요구하지 않으면 위 표보다 늘리지 않는다.

## 3. 실행 방법

실행 환경에 따라 다음 순서로 고른다.

1. **하위 에이전트를 부를 수 있으면(Claude Code의 Agent 도구 등)** 검토자마다 새 하위 에이전트를 한 번 호출한다. 관점 검토자들은 서로 의존하지 않으므로 한 번에 병렬로 부른다. 누락 검토자는 관점 검토 결과가 모두 모인 뒤 부른다. 대화할 필요가 없고 결과만 받으면 되므로 단발 호출로 충분하다.
2. **하위 에이전트를 부를 수 없으면(Codex 단일 세션 등)** 작성자가 역할을 바꿔 순서대로 검토한다. 이때 작성할 때의 판단 이유를 떠올리지 말고 4절의 입력 파일만 다시 연다. 역할마다 결과 표를 `03_review_{역할}.md`로 따로 남긴다. 같은 맥락에서 하는 검토라는 한계를 gate 파일에 `검토 방식: 단일 세션 역할 전환`으로 기록한다.

모델을 고를 수 있는 환경이면 게이트 검토자처럼 절차가 정해진 검사는 빠른 모델로, 관점 검토와 적대적 확인처럼 판단이 필요한 검토는 추론이 강한 모델로 부른다. 모든 검토자에 같은 고성능 모델을 일괄 지정하지 않는다.

## 4. 검토자에게 넘기는 입력

검토자는 작성 과정을 보지 않아야 한다. 다음만 넘긴다.

- 역할 이름과 이 문서의 해당 역할 행, 5절 결과 형식
- 파일 경로(하위 에이전트는 작업 위치가 다를 수 있으므로 모두 절대경로로 넘긴다): `docs/PRD.md`(또는 draft), `docs/00-pm/*.prd.md`, 업무 브리프, `docs/00-pm/_workspace/01_mapping.md`, 스킬 폴더의 `references/gate-checklist.md`·`references/brief-mapping.md`
- `01_mapping.md`는 브리프의 어느 항목이 PRD 어디로 갔는지 찾는 **색인으로만** 쓴다. 매핑이 맞는지는 검토자가 브리프 원문과 PRD를 직접 대조해 판단하고, 메모를 근거로 결함을 기각하지 않는다. 메모가 없으면(외부에서 만든 PRD를 검토할 때) 브리프와 PRD를 직접 대조하고 gate 파일에 `작업 메모 없음`을 쓴다.
- 게이트 검토자에게는 `node scripts/validate_prd.mjs` 실행 결과도 넘기거나 직접 실행하게 한다
- 읽기만 하고 파일을 고치지 말라는 지시

작성자의 판단 이유나 "이 부분은 의도적이다" 같은 설명은 넘기지 않는다. 설명이 필요한 결정은 PRD 13장이나 근거 라벨에 이미 있어야 한다. 없으면 그것 자체가 결함이다.

## 5. 결과 형식

각 검토자는 다음 표 하나만 반환한다. 결함이 없으면 `결함 없음`과 대조한 범위를 한 줄로 쓴다.

| 번호 | 심각도 | 위치 | 문제 | 근거(대조한 양쪽) | 수정안 | 결정권자 |
|---|---|---|---|---|---|---|
| R-01 | Blocker · Major · Minor | 장·ID·표 행 | 한 문장 | 예: 브리프 4장 "반려" ↔ PRD 8장에 없음 | 한 문장 | [작성자] · [구현자] |

- 심각도는 `references/gate-checklist.md` 11절 기준을 따른다.
- 근거 없이 "모호하다", "부족하다"만 쓴 결함은 받지 않는다.
- 검토자는 PRD에 없는 사실을 만들어 결함 근거로 쓰지 않는다.

## 6. 적대적 확인

검토자가 Blocker를 잘못 판정하면 쓸데없이 착수 불가가 되고, 놓치면 bkit이 다른 제품을 만든다. 그래서 2절에서 정한 심각도의 결함은 확인을 한 번 더 거친다.

1. 검토자 결과 표 하나마다 확인자 1명에게 그 표의 확인 대상 결함을 한꺼번에 넘기고 "각 결함을 반박할 근거를 PRD와 브리프에서 찾아라"라고 맡긴다. 결함마다 확인자를 따로 두지 않는다. 확인할 결함이 많아도 호출 수가 검토자 수를 넘지 않게 하기 위해서다.
2. 판정은 `확인됨`(근거가 맞고 반박 불가), `반박됨`(PRD에 이미 해결돼 있음, 근거를 인용), `불확실` 중 하나다.
3. `확인됨`만 게이트에 반영한다. `반박됨`은 gate 파일에 반박 근거와 함께 남기고 반영하지 않는다. `불확실`은 심각도를 한 단계 낮춰 반영하고 13장 확인 요청 후보로 둔다.
4. Full 모드의 Blocker는 Blocker 전체를 확인자 3명에게 한꺼번에 넘기고, 결함마다 2명 이상이 `확인됨`일 때만 Blocker로 반영한다. 확인자마다 정확성, 구현 가능성, 브리프 충실도처럼 다른 기준을 준다.
5. 7절 재검토에서 새로 나온 결함만 다시 확인한다. 이미 확인된 결함은 다시 확인하지 않는다.

## 7. 반복과 종료

1. 작성자가 확인된 결함을 정본에 반영한다. 파생본은 정본에서 다시 만든다.
2. 게이트 검토자를 다시 부른다. 고친 ID와 그 연결만 보게 한다. 관점 검토자는 Blocker를 고친 경우에만 다시 부른다.
3. 최대 2회 반복한다. 2회 뒤에도 Blocker가 남으면 draft로 저장하고 남은 결함을 13장 결정 요청으로 올린다.
4. 같은 결함이 반복해서 나오면 그 행만 고치지 말고 원인(대응표 누락, 템플릿 열 누락 등)을 찾아 고친다.

## 8. 작업 폴더

중간 산출물은 `docs/00-pm/_workspace/`에 `{순서 번호}_{내용}`으로 저장하고, 검토자 결과만 `03_review_{역할}.md`로 역할을 붙인다. 역할 이름은 `gate`·`business`·`build`·`verify`·`missing`을 쓴다. 다음 요청에서 일부만 다시 실행하고, 판정 근거를 나중에 확인하기 위해서다.

| 파일 | 내용 |
|---|---|
| `00_input.md` | 읽은 입력 목록·버전·브리프 추출 결과 |
| `01_mapping.md` | Step 2 작업 메모(입력 매핑 12개 표) |
| `02_validate.txt` | `validate_prd.mjs` 출력과 종료 코드 |
| `03_review_{역할}.md` | 검토자별 결과 표 |
| `04_verify.md` | 적대적 확인 판정 |
| `05_gate_summary.md` | 반영한 결함·반박된 결함·반복 횟수 |

- 새 브리프로 처음부터 다시 만들면 기존 `_workspace/`를 `_workspace_{YYYYMMDD-HHMM}/`로 옮긴 뒤 시작한다.
- 같은 PRD의 일부만 고치면 기존 파일을 유지하고 해당 단계 파일만 새로 쓴다.
- `_workspace/`는 지우지 않는다. 최종 산출물은 정본·파생본·gate 파일이다.

## 9. 오류 처리

- 검토자 호출이 실패하면 한 번 다시 부른다. 또 실패하면 그 관점 없이 진행하고 gate 파일에 `미실행 관점: {역할} — 사유`를 쓴다. 미실행 관점이 있으면 판정은 최대 `조건부 착수`다.
- 사용량 한도·권한 거부처럼 다시 불러도 결과가 같은 실패는 다시 부르지 않는다. 끝난 검토 결과만으로 판정하고 사용자에게 알린다.
- 검토자가 남기지 못한 판단을 작성자가 추측해 채우지 않는다. 직접 확인한 사실만 gate 파일에 쓴다.
- `node`를 실행할 수 없어 기계 검사를 못 하면 gate 파일에 `기계 검사 미실행`을 쓰고 Major 1건으로 센다. 통과로 간주하지 않는다.
